# Fixed-endpoint preparation in existing Q dynamics

This workflow prepares a starting endpoint for a charge-only molecular dynamics
(MD) ladder. It adds no sampler, thermostat, integrator or force model. A completed
preparation schedule is **not an equilibrated endpoint certificate**. Temperature,
geometry, solvent response and independent-replica diagnostics remain necessary.
No high-performance computing (HPC) calculation is submitted by the planning tool.

## Explicit schedule and budget

Use a fresh synthetic probe/water preparation for each sign, direction and replica,
with recorded, distinct orientation and initial-velocity seeds. The unchanged
three-site transferable intermolecular potential water model (TIP3P), real probe
Lennard–Jones (LJ, repulsion/dispersion) parameters and restraints are those in the
[pilot protocol](PILOT_PROTOCOL.md). Different seeds do not establish equilibrium
independence; copying a final restart does not create another independent replica.

The proposed starting protocol is fixed at 298 kelvin and at the intended starting
endpoint throughout: state-2 weight zero for forward, one for reverse. Pure-state
identities remain charge 0 and the declared sign. There is no heating ramp or
gradual charging phase. Direct initialization at either endpoint is a testable
preparation choice, not a claim that grid water is relaxed or that 100 picoseconds
(ps) suffice. If it does not settle within the cap, preserve the failure and revise
the experimental plan; do not silently add time or tune the boundary model.

At the candidate one-femtosecond (fs) timestep, the 100 ps cap includes:

- A 20-step, 0.02 ps grid-start seed generated by the existing bounded probe tool.
  This initializes velocities and frozen zero angular offsets, not an ensemble.
- Four 20,000-step continuation segments and one 19,980-step segment.
  The complete preparation is exactly 100,000 steps, including the seed.

At 0.5 fs the generator translates physical durations to step counts and still
includes the 20-step seed in the same 100 ps cap. Each segment must retain energy
records. Durations and any final remainder must therefore be representable in
ten-step increments, with at least twenty steps per continuation segment. Failed
attempts count against the experimental allocation; the tool does not retry them.

The default continuation requires an approved longer-calculation budget. The
existing chain runner's default 2,000-step per-call limit refuses a 20,000-step
segment; generating the plan does not authorize running it.

## Restart velocities: an important Q input convention

In Q, a **positive** `random_seed` calls the existing Maxwell velocity initializer,
even if a restart supplied velocities. A seed of **zero** retains restart velocities.
This follows the `iseed > 0` branch in `src/q6/qdyn.f90`, after restart loading in
`prep_coord`. The input parser also zeroes the seed if `initial_temperature` is
omitted, but this restricted protocol keeps that field explicit.

The grid-start seed uses a positive seed. Every endpoint continuation uses
`random_seed 0`, while keeping the explicit temperature fields at 298. The staged
validator records `velocity_initialization: restart` or `maxwell` and rejects
mixing these strategies within a chain. Positive-seed historical/software-test
inputs are not rewritten or reinterpreted as velocity-continuing trajectories.

Q's existing input log contains an unconditional “Initial velocities will be
generated” sentence, even for seed zero. Do not infer execution from that sentence.
The native regression changes only restart velocities on fixed coordinates:
positive seeds erase the difference in the final restart, whereas zero retains
its effect. This tests the actual branch, not just a manifest label. It does not
prove split runs are bitwise identical to uninterrupted trajectories or establish
canonical sampling by Q's existing thermostat.

## Prepare, plan and inspect

First build a retained Qdyn/Qprep pair using the
[isolated build workflow](BUILD_AND_CHAIN.md). Use **that build's** executables
for the fresh `charge_probe prepare` and 20-step `charge_probe timing` commands.
For a forward seed use weight zero; for reverse use weight one, with the desired
charge sign. Keep all generated assets and reports.

The planner consumes the existing reports and writes a **new** directory:

```sh
PYTHONPATH="$PWD/src" python -m QligFEP.charge_endpoint \
  /path/to/prepared/prepared.json /path/to/seed/timing.json \
  /path/to/build/build.json /path/to/new-endpoint \
  --sign=-1 --direction reverse --replica 1 --total-ps 100 --segment-ps 20
PYTHONPATH="$PWD/src" python -m QligFEP.charge_chain inspect \
  /path/to/new-endpoint/plan.json
```

The planner executes no MD. It verifies source-build identities, retained asset
fingerprints, seed inputs, endpoint sign/weight, effective radius, timestep and
zero offsets. Fingerprints use SHA-256, a cryptographic hash algorithm. The seed
report remains a limited grid-start/timing check, not a full trajectory audit.
The planner preserves a failed output directory instead of overwriting it.

The plan uses JavaScript Object Notation (JSON) schema version 2 with
`purpose: endpoint_preparation` and a pinned `preparation` origin/budget record.
Existing version-1 charge ladders remain full monotonic endpoint-to-endpoint
transformations; this new purpose does not relax their requirements. The same
one-window chain runner audits each realized segment and its predecessor, preserves
failed attempts and refuses output overwrite. Origin assets are rechecked on
every invocation, not merely trusted from the plan's first creation.

The chain report's `total_steps` counts its continuation segments; the nested
`preparation_origin.total_steps` and `total_ps` include the grid seed. The nested
`equilibrated` and `independent_replica_established` fields remain false after
normal completion. The Bennett acceptance ratio (BAR) analysis explicitly rejects
endpoint-preparation plans: repeated endpoint samples are not a free-energy ladder.

## Remaining qualification

This implements bounded, traceable endpoint preparation, not the complete campaign
generator. Cross-replica seed/system checks, transfer of a qualified endpoint into
a charge ladder, trajectory/runtime diagnostics and the campaign-level statistical
comparisons remain required. Full pilot/HPC submission still needs user approval.
No existing angular target, adaptive-offset history or archived result was changed.

Verification checkpoint (2026-09-08): **275 passed, 2 optional integration skips,
2 documented archival partition expected failures**, in 73.92 seconds. Native
tests exercise both signs/directions, short repeated-endpoint continuations,
velocity retention versus regeneration, and unchanged frozen offsets. Tests also
check both timestep budgets, origin/input mutations, invalid budgets, planning
without MD execution, command-line output and refusal to overwrite an existing plan. Only
Python workflow/analysis validation, tests and documentation changed; the native
MD code was not modified. No long preparation or HPC job was run.
